# ETL 数据监控 CleanVibe 修复设计

## 问题

1. `src/App.tsx` 已登记 4 个 411 需求，但迭代栏固定只渲染重试策略，导致 ETL URL 与顶部入口不一致。
2. ETL 日期状态先写入目标汇总态，再据此生成明细并重新聚合，无法验证混合任务优先级。
3. 错误码仅用于提示展示，没有参与任务最终状态判定。

## 设计

### 需求入口

迭代栏直接渲染 `iterationRequirements` 中的全部需求，不再写死过滤条件。现有 URL 校验、默认门户映射、PRD/原型切换和标注入口保持不变。

### 状态模型

在 `src/pages/etlDataMonitoringOptimization/` 内新增纯状态模块，职责限定为：

- 根据取数、入库、校验三个阶段事实判定单条任务的最终状态。
- 取数阶段 `1xxx` 判定为异常，`2xxx/3xxx` 判定为失败。
- 任一入库错误判定为失败。
- 入库成功后校验不通过判定为异常。
- 尚未结束判定为等待；成功入库且校验关闭或通过判定为成功；无实际任务判定为无任务。
- 聚合时忽略与实际任务并存的无任务，按“失败 > 异常 > 等待 > 成功”取最高优先级。

页面 Mock 改为先生成相互独立的任务阶段事实，再调用分类和聚合函数。下钻表继续只展示三段状态，不增加最终状态、问题阶段、错误码或原因独立列。

## 测试与验收

- 使用 Node 22 原生测试运行 TypeScript 纯函数，不新增依赖。
- 测试覆盖 1xxx、2xxx/3xxx、入库错误、校验异常、等待、成功、全无任务、无任务与实际任务混合、混合状态优先级。
- 先确认新测试因实现缺失而失败，再写最小实现使其通过。
- 运行 `npm run build` 和定向 CleanVibe。
- 在 5177 真页验证 4 个需求入口、ETL 直达、店铺/数据表最终状态、下钻三段状态、7 条标注和 console。

## 范围边界

- 不重构整个 ETL 页面。
- 不修改真实后端或下载源码副本。
- 不调整 PRD 已确认的状态口径、列结构和标注文案。
- 不处理当前工作树中其他需求的历史复杂度。
