# ETL 数据监控重试后的父子状态一致性设计

## 1. 问题与目标

店铺维度和数据表维度都可从父表日期状态下钻到执行明细。当前重试只更新父表聚合结果，子表仍展示重试前的三段状态，可能出现父表成功、子表仍为“取数执行失败／数据入库失败／数据校验无任务”的矛盾。

本次目标是建立一套统一的当前执行口径：父表和子表都基于同一条业务明细的最新有效执行结果展示，重试的受理、执行和完成过程均可解释、可刷新、可验收。

## 2. 已确认方案

1. 同一业务明细在子表中始终保留一行，不因重试新增明细行。
2. 重试受理后，将新尝试切换为该业务明细的“当前有效执行”；旧尝试仅保留在日志和运行记录中。
3. 重试受理后立即展示新执行的等待状态，不继续展示旧失败；父表同时按新状态重新聚合。
4. 店铺父表、数据表父表及其下钻子表共用该口径，不允许父表读取最新尝试、子表读取原尝试。

## 3. 对象与数据口径

### 3.1 业务明细

业务明细由当前下钻对象、业务日期、关联计划、店铺和数据表共同定位。它是子表中的稳定行身份，重试不会改变该身份。

### 3.2 执行尝试

一次原始执行或重试均是一条执行尝试。每条业务明细只能有一个当前有效执行尝试；其余尝试是历史记录。

前后端交互至少需要能够识别以下逻辑信息，具体接口字段名不在原型中约束：

- 业务明细标识；
- 当前有效执行标识或版本；
- 取数执行、数据入库、数据校验三段原始状态；
- 当前阶段、失败原因和错误码；
- 重试类型及是否仍在执行；
- 本次计划超时阈值与运行时长。

父表聚合与子表展示必须引用同一当前有效执行版本。接口暂不可用时，原型仅模拟该行为，不把 mock 数据当作生产接口事实。

## 4. 整体状态流程

### 4.1 提交前

子表展示当前有效执行的三段状态。失败记录按现有权限和可重试条件展示“重试”；历史尝试通过“日志／运行记录”查看。

### 4.2 提交中

用户选择重试类型并确认后，当前行重试入口进入 loading 且禁止重复提交。服务端尚未确认受理前，三段状态和父表聚合均保持不变。

### 4.3 受理成功

服务端确认重试受理后，新尝试成为当前有效执行。子表立即切换到新尝试的等待状态，父表使用相同最新状态重新聚合。

- 重试采集：取数执行＝等待，数据入库＝无任务，数据校验＝无任务。
- 重试入库：保留当前有效的取数成功结果，数据入库＝等待，数据校验＝无任务。

“无任务”表示该新尝试尚未进入后续阶段，不代表整条业务明细没有计划。父表聚合时，只要该明细存在等待阶段，就按等待参与聚合。

### 4.4 执行中

子表自动刷新当前行，展示新尝试各阶段的最新状态。父表使用同一数据源按最新状态重新计算；返回父表、切换父表维度或点击主动刷新时，均重新获取最新有效执行。

### 4.5 执行完成

- 重试成功：子表展示新尝试最终三段结果；校验正常、无数据或无需校验沿用现有前端映射显示为成功。父表据此重新聚合。
- 重试失败：子表展示新尝试实际失败的阶段、错误码和原因，未执行的下游阶段展示无任务；父表据此重新聚合。
- 旧执行尝试不再参与当前状态展示和父表聚合，但继续保留在日志和运行记录中。

## 5. 父表聚合规则

店铺父表和数据表父表均先取得所属业务明细的当前有效执行结果，再按“失败 ＞ 异常 ＞ 等待 ＞ 成功”聚合。

1. 重试受理后，如果原失败明细已变为等待且同组没有其他失败或异常，父表变为等待。
2. 如果同组仍有其他失败明细，父表继续显示失败，不因单条明细进入重试而变为等待。
3. 重试成功后，只有同组所有当前有效执行都满足成功口径，父表才显示成功。
4. 重试再次失败后，父表显示失败，原因来自最新有效执行，不展示旧尝试原因。
5. 计划运行超时仍按每个计划本次执行实际生效的阈值判定；重试不会使用后续修改后的阈值回算历史尝试。

## 6. 异常与恢复

- 重试提交失败：不创建或切换当前有效执行，保留原三段状态，恢复重试入口并提示“重试提交失败，请重试”。
- 状态刷新失败：保留最后一次已确认状态，提示刷新失败；不得把未知结果推定为成功。
- 页面离开后返回：重新查询当前有效执行，不恢复组件内缓存的旧状态。
- 重复提交：同一当前执行在提交中禁用重试；受理后按现有可重试规则决定是否允许再次操作。
- 查询结果版本落后：不得用旧版本覆盖页面上已经确认的新版本。

## 7. 原型、交互标注与 PRD 落点

### 7.1 可运行原型

在店铺下钻与数据表下钻复用同一重试状态流。原型需直接演示：原失败、提交中、受理后等待、最终成功、最终失败和提交失败，并同步刷新当前子表行与对应父表日期状态。

### 7.2 交互标注

优先使用可操作的前端演示说明重试过程，文字仅补充数据口径、父表聚合和异常边界。标注覆盖两种下钻，但共用一条重试一致性规则，避免分别重复大段说明。

### 7.3 PRD

在核心流程、父表状态聚合、下钻明细、重试交互、异常恢复和验收标准中明确当前有效执行口径。PRD 不把原型 mock 状态、定时器或字段名写成生产接口实现。

## 8. 验收标准

以下场景需分别覆盖店铺下钻和数据表下钻：

1. 重试采集受理后，当前行变为“等待／无任务／无任务”，父表同步按等待重新聚合。
2. 重试入库受理后，保留取数成功，入库变为等待，校验变为无任务，父表同步重新聚合。
3. 重试成功后，子表显示最新成功结果；返回父表或主动刷新时父表结果一致。
4. 重试失败后，子表展示最新失败阶段和原因，父表为失败；旧失败原因仅在历史日志中存在。
5. 重试提交失败时，父子状态均不变化，入口恢复可操作并出现失败提示。
6. 状态刷新失败时保留最后确认结果，不显示虚假成功；恢复刷新后更新到最新结果。
7. 同组仍存在其他失败或异常时，父表按最高优先级聚合，不被单条重试状态覆盖。
8. 连续快速点击不会产生重复有效提交，旧版本响应不会覆盖新版本状态。

## 9. 本期边界

本期定义并演示重试后的展示、刷新和父子聚合一致性，不新增自动重试策略，不修改现有重试权限，不删除历史执行记录，也不约束生产接口的具体 URL 和字段命名。
